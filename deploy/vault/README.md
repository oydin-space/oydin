# Vault для секретов Oydin

Самохостный HashiCorp Vault (`hashicorp/vault:2.1.2`). Transit-ключ `oydin-creds` шифрует пароли Didox и секреты коннекторов (`DidoxAccount.password_enc`, `Connector.auth_secret_enc`). В базе лежит только шифртекст `vault:v1:…`; ключ из Vault не выходит.

- Хранилище: файловое, том `vault_data`. Сеть `vault` internal: порт наружу не публикуется, у контейнера нет выхода в интернет. К ней подключён только `api` (единственный сервис, читающий секреты коннекторов и пароли Didox); `webhooks` и `botjobs` токена Vault не получают.
- Пока `VAULT_ADDR` пуст и `VAULT_REQUIRED=0` (по умолчанию), приложение шифрует Fernet от `DJANGO_SECRET_KEY` (как раньше): безопасный режим выкатки, пока оператор не инициализировал Vault. Старые значения читаются и при первом чтении перешифровываются в Vault (условной записью: параллельно сохранённый новый секрет не затирается).
- `VAULT_REQUIRED=1` (оператор включает в `.env` после шагов 1-11) запрещает отступать на Fernet: при пустом `VAULT_ADDR`/`VAULT_TOKEN` запись секрета отдаёт `vault_unavailable` (503), а не пишет слабый шифртекст. Потерянная или опечатанная строка `.env` перестаёт быть тихой.
- `VAULT_LEGACY_READ=0` (после того как `vault_reencrypt` показал нулевой остаток) отключает чтение старых Fernet-значений. Бэкапы и WAL до миграции остаются расшифровываемыми `DJANGO_SECRET_KEY`: существовавшие до перехода пароли Didox и секреты коннекторов ротируйте или вычистите старые бэкапы.
- Нерасшифровываемое Fernet-значение (например, после смены `DJANGO_SECRET_KEY`) больше не считается «секрета нет»: чтение даёт ошибку, Didox просит переподключиться (`didox_reconnect_required`), а не логинится пустым паролем.
- Конфиг: `vault.hcl`. Политика токена приложения: `oydin-app.hcl` (только encrypt/decrypt ключом `oydin-creds`).

## Правила обращения с секретами

Unseal-ключ и root-токен показываются **один раз**, в терминале оператора. Не писать их в репозиторий, `.env`, логи, тикеты и историю shell. Хранить в менеджере паролей, лучше разделить. Потеря unseal-ключа = потеря всех зашифрованных секретов: восстановить их нельзя, пользователям придётся ввести пароли Didox и секреты коннекторов заново. Токен приложения (`VAULT_TOKEN`) единственный секрет Vault, который попадает в `~/oydin/.env` (chmod 600).

Все команды `vault` ниже выполняются внутри контейнера, без секретов в аргументах и в окружении.

## Однократная инициализация

1. Поднять Vault: `cd ~/oydin && docker compose up -d vault`, затем `docker compose ps vault` (статус healthy: процесс отвечает; запечатанный Vault тоже healthy).
2. Инициализация с делением ключа 3 из 5 (доли раздайте разным людям; порог 1 из 1 означает, что утечка одного значения распечатывает всё):

   ```sh
   docker compose exec vault vault operator init -key-shares=5 -key-threshold=3
   ```

   Вывод содержит `Unseal Key 1-5` и `Initial Root Token`. Сразу перенести их в менеджер паролей. Не копировать вывод в файлы, чат и логи CI. Команда повторно секреты не покажет.
3. Распечатать: команда выполняется три раза, каждый раз с другой долей (ввод скрытый, не аргументом):

   ```sh
   docker compose exec vault vault operator unseal
   ```

4. Зайти root-токеном в интерактивной сессии контейнера (ввод скрытый; токен остаётся в памяти сессии и в `~/.vault-token` внутри контейнера):

   ```sh
   docker compose exec -it vault sh
   vault login            # вставить Initial Root Token
   ```

   Дальше команды 5-8 выполнять в этой же сессии.
5. Включить Transit и создать ключ (экспорт запрещён по умолчанию, ключ не exportable):

   ```sh
   vault secrets enable transit
   vault write -f transit/keys/oydin-creds derived=true
   ```

   `derived=true` обязателен и задаётся до первого шифрования: приложение передаёт `context` = тип записи, бизнес и поле, поэтому шифртекст одного арендатора не расшифровывается в записи другого (копирование строки в БД не помогает). Ключ без `derived` с этим кодом не работает.

6. Загрузить политику (файл примонтирован из репозитория, только чтение) и включить аудит (журнал на томе `vault_logs`, значения хешируются HMAC; настройте ротацию журнала):

   ```sh
   vault policy write oydin-app /vault/policies/oydin-app.hcl
   vault audit enable file file_path=/vault/logs/audit.log
   ```

7. Создать периодический токен приложения. Он выводится один раз; скопировать его только в `VAULT_TOKEN` файла `~/oydin/.env`:

   ```sh
   vault token create -policy=oydin-app -no-default-policy -period=720h -orphan -display-name=oydin-app
   ```

   Поле `token` из вывода и есть `VAULT_TOKEN`. Периодический токен (30 дней) живёт, пока его продлевают: см. «Продление». Политика `default` не выдаётся.
8. Отозвать root-токен и выйти. Root для новых задач создаётся заново через `vault operator generate-root` и unseal-ключ:

   ```sh
   vault token revoke -self
   rm -f ~/.vault-token
   exit
   ```

9. В `~/oydin/.env` выставить (chmod 600, редактором, не через `echo` в историю):

   ```
   VAULT_ADDR=http://vault:8200
   VAULT_TOKEN=<токен из шага 7>
   ```

   `VAULT_REQUIRED=1` добавьте только после шага 11 (Vault инициализирован, распечатан, проверен): с этого момента откат на Fernet запрещён. Пока оператор не готов, оставьте `0`.

10. Применить и перенести существующие секреты:

    ```sh
    docker compose up -d api webhooks botjobs
    docker compose exec api python manage.py vault_reencrypt
    ```

    Команда идемпотентна и печатает число перешифрованных значений. Не перенесённое она не теряет: значения доедут лениво при первом чтении.
11. Проверка: подключить/синхронизировать Didox или вызвать коннектор в интерфейсе; в базе значения начинаются с `vault:v1:`. Ошибка `vault_unavailable` в ответах = Vault запечатан или недоступен.

## После каждого рестарта сервера или контейнера

Vault стартует запечатанным (нужны три доли ключа). Пока он запечатан, чтение и сохранение секретов отдаёт `vault_unavailable` (503), остальное приложение работает.

```sh
docker compose exec vault vault operator unseal   # три раза, разные доли
```

## Продление токена приложения

Период токена 30 дней: продлевать каждые 2-3 недели (по календарю оператора). Токен приложения вводится скрытым запросом, не аргументом:

```sh
docker compose exec -it vault sh
vault login            # вставить VAULT_TOKEN из .env
vault token renew-self
vault token lookup-self | grep -E 'ttl|period'
rm -f ~/.vault-token
exit
```

Если токен истёк или скомпрометирован: пройти шаги 4, 7 и 9 заново (root через `vault operator generate-root`), старый отозвать по accessor, а не по значению токена (иначе он окажется в аргументах и истории): `vault token revoke -accessor <accessor>` (accessor показывает `vault token lookup-self` и вывод шага 7). Журнал аудита покажет, чем пользовались токеном.

## Откат

Вернуть `VAULT_ADDR=` и `VAULT_TOKEN=` пустыми не вернёт доступ к уже перешифрованным значениям: `vault:v1:…` читается только через Vault. Откат также требует `VAULT_REQUIRED=0`. Для отката сначала расшифровать значения, пока Vault работает, либо попросить пользователей переввести секреты. Новые значения без Vault снова будут шифроваться Fernet.

## Резервная копия

Том `vault_data` (шифртекст ключей) копируется только вместе с unseal-ключом, хранящимся отдельно. Без любой из двух частей копия бесполезна.
